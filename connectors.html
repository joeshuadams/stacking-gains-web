User setup in the candidate app

  1. Open Settings → Connections → Muse and check SG Connect access.
  2. Follow the assistant's custom-connector instructions, then authorize your own SG account and review permissions. Until a directory entry is available, setup can involve copying a public URL or non-secret setup instructions. OAuth does not require copying a bearer token into a chat.
  3. Start with read and log. Ask the assistant to read a saved meal or log food with portions and an intended date.
  4. Check the saved entry and totals in SG. The assistant must confirm the saved result before saying it logged a meal.

SG stores the nutrition values submitted by the assistant. Estimates are not measurements; review portions and correct inaccuracies. Your assistant provider's subscription, if required, is separate from SG.

Disconnect in Connections to stop future access. Revocation does not erase records already shared with the assistant provider; that provider's privacy and retention settings still apply.

Protocol and discovery

Production candidate origin: https://stacking-gains-production.up.railway.app. The current service does not yet expose the candidate OAuth discovery endpoint. Reviewers receive isolated test access before testing; do not use real nutrition records in staging.

Protected resource: {origin}/api/mcp
Authorization metadata: {origin}/.well-known/oauth-authorization-server
Resource metadata: {origin}/.well-known/oauth-protected-resource/api/mcp
  • Remote MCP uses JSON-RPC 2.0 over HTTPS POST with JSON responses. Initialize with protocol version 2025-06-18. No server-to-client SSE stream is offered.
  • Discover authorization, token and client-registration endpoints from metadata. Public clients use authorization code with S256 PKCE, an exact registered redirect URI, and token_endpoint_auth_method: none.
  • Request read log offline_access and the MCP resource. Offline access enables refresh, not broader editing permission. Rotate stored refresh credentials securely.
  • Send access tokens only in the HTTPS Authorization bearer header. Never include credentials in prompts, URLs or logs.
  • An initialized notification has no ID and can return HTTP 202 with an empty body. Do not parse that empty response as JSON.

Permissions

read
Read exposed targets, food history, summaries, saved meals and modes.
log
Add food and undo entries created by this same connection. Does not permit editing arbitrary past/manual entries or changing targets.
manage
Additional food and plan editing, separately authorized. Excluded from the initial Muse setup.

Use only tools returned by tools/list; those schemas are authoritative. The initial workflow uses get_targets, list_presets, get_day, log_food and undo_log. Account and billing administration are not MCP permissions.

Reliable writes

Each intended meal needs a unique idempotency_key of 8–128 characters. Retry an uncertain write with the same key and unchanged arguments. A different payload under that key is rejected. A deliberate new meal needs a new key, even when the food is identical.

Example for an isolated review account:

{
  "jsonrpc": "2.0",
  "id": 3,
  "method": "tools/call",
  "params": {
    "name": "log_food",
    "arguments": {
      "idempotency_key": "review-meal-20260924-unique-01",
      "item": "Synthetic review meal",
      "meal": "Lunch",
      "date": "2026-09-24",
      "timezone": "America/Los_Angeles",
      "cal": 400, "pro": 30, "carb": 40, "fat": 13,
      "servings": 1
    }
  }
}

Check top-level JSON-RPC errors and result.isError. Successful food results encode JSON in result.content[0].text, including logged.id and totals. Use get_day with an explicit date to verify the record. undo_log takes {"id": "the saved entry ID"}; retrying the original write after undo must not recreate it.

Use preset with an existing saved-meal name when appropriate. Supply the user's timezone, preserve the intended local date, and inspect the day's stored goals rather than substituting today's mode for historical goals.

Access and recovery

SG Connect eligibility is checked on the server. Apple in-app subscriptions with RevenueCat verification are being prepared; public purchases are not yet live. The connector does not accept payments through Muse.

401 — sign-in required
Credentials are missing, invalid or revoked. Reconnect through authorization; never ask the user for an SG session token.
403 — access or permission denied
Open SG to review SG Connect access and connection permissions. Use Restore purchases if already subscribed. Do not assume every denial means an expired subscription.
503 — verification or service unavailable
If rejected at the access gate, no tool was executed. Retry later; do not recommend a new purchase because verification failed.
429 — too many requests
Respect Retry-After. Do not loop or register replacement clients to bypass limits.
Uncertain write result
Reuse the same idempotency key and inspect the day's diary. An HTTP status alone does not prove that a meal was saved.

End-to-end review

  1. Authorize a synthetic account with read log offline_access; verify the intended identity and displayed permissions.
  2. Initialize, list tools, then read targets, presets and a dated food log.
  3. Save one synthetic meal. Repeat the same key and payload; confirm one row. Reuse that key with changed values; confirm rejection.
  4. Open SG and check the date, entry and dashboard without manual refresh. Undo the saved entry and confirm it is removed.
  5. Confirm read/log permission cannot change targets or another account's records.
  6. Disconnect and verify that old access and refresh credentials fail.
  7. In the controlled billing test environment, verify no-access and verification-outage responses without executing a tool.

Directory acceptance, featured placement, other assistants and native purchase verification are separate checks. This documentation does not establish those outcomes.
